# DevStation 测试与质量防护体系

## 1. 文档目的

本文档定义 DevStation 的测试范围、质量门禁、测试编写原则和演进方式，用于指导开发、评审和持续集成。

测试体系的目标不是追求测试数量或覆盖率数字，而是持续拦截以下风险：

- 用户关键链路发生功能回归
- Electron 进程边界、安全边界或资源生命周期被破坏
- 数据迁移、持久化和多处状态缓存不一致
- Main、Preload、Renderer、Shared 出现反向依赖或循环依赖
- 依赖漏洞、许可证、原生模块或安装包问题进入交付物

本体系适用于当前 Windows 优先的 Electron MVP。多平台兼容、签名、SBOM、安装升级矩阵将在进入正式发布阶段后补充。

## 2. 核心原则

### 2.1 测试必须保护可观察行为

优先测试输入、输出、状态变化、外部调用边界和资源生命周期，不测试私有实现步骤。重构内部实现但保持契约不变时，测试原则上不应失败。

一个测试至少应保护下列一种风险：

- 关键业务规则
- 安全或权限边界
- 数据一致性或迁移兼容性
- 异步、并发或资源清理行为
- 曾经发生过且可能复发的缺陷
- 跨进程、跨模块或第三方依赖契约

无法说明所保护风险的测试不应加入测试集。

### 2.2 风险决定测试层级

能够由单元测试稳定覆盖的逻辑不放到 E2E；只有跨 Electron 进程、真实渲染、真实 PTY 或持久化重启链路才使用较重的测试。测试应尽量靠近故障来源，同时保留少量端到端黄金链路验证整体接线。

### 2.3 正常路径和失败路径同等重要

高价值模块必须覆盖参数边界、权限拒绝、依赖失败、数据不存在、重复操作、窗口销毁和进程退出等失败路径。只验证正常路径不足以构成防护。

### 2.4 测试必须可重复和隔离

- SQLite 测试使用独立临时数据库，不依赖开发者本地数据。
- Electron E2E 使用独立临时 `userData`，不得读写真实用户目录。
- 测试不得依赖执行顺序、已有项目、已有会话或外部登录状态。
- 时间、进程、文件系统和原生对话框只在必要边界替换；业务逻辑本身不应被 Mock 掉。
- Playwright 当前不启用重试，避免用重试掩盖不稳定测试。

### 2.5 缺陷必须沉淀为回归测试

修复缺陷时，先在最靠近根因的层级构造可复现测试，再修复实现。只有无法自动化或自动化成本明显高于风险时，才允许记录人工验证步骤。

## 3. 防护体系分层

| 层级         | 保护对象                        | 主要工具                     | 当前内容                                 |
| ------------ | ------------------------------- | ---------------------------- | ---------------------------------------- |
| 静态质量     | 类型、语法、格式                | TypeScript、Oxlint、Prettier | Node/Web 类型检查、Lint、格式一致性      |
| 架构边界     | 模块方向和循环依赖              | dependency-cruiser           | Main、Preload、Renderer、Shared 依赖规则 |
| 单元测试     | 领域逻辑和边界条件              | Vitest                       | 数据库、Git、RPC、终端生命周期、Store    |
| 组件测试     | React 交互和状态呈现            | Testing Library、jsdom       | 任务面板、会话列表、危险操作确认         |
| 集成测试     | 数据库、RPC、文件系统、进程协作 | Vitest、临时目录、真实 Git   | SQLite 迁移、Repository、Git 仓库识别    |
| Electron E2E | 用户黄金链路和跨进程接线        | Playwright Electron          | 持久化恢复、删除确认、项目引用约束       |
| 原生冒烟     | PTY 和 CLI Agent 真实运行       | Electron、node-pty           | PTY I/O、resize、Codex 启动和退出        |
| 供应链       | 依赖完整性、漏洞和许可证        | npm、许可证脚本              | 依赖树、高危漏洞、生产依赖许可证白名单   |
| 交付物       | Windows 可安装性                | electron-builder             | Windows x64 NSIS 安装包构建              |

## 4. 当前重点测试契约

### 4.1 SQLite 与 Repository

必须保护：

- 新数据库初始化和 schema 版本
- 历史版本逐步迁移、迁移失败回滚和重开
- 高版本数据库拒绝降级打开
- 外键、唯一性、级联删除和限制删除
- Task、Project、Session CRUD 及排序语义
- 数据库关闭后的调用拒绝

测试位置：`src/main/db/__tests__/`

### 4.2 RPC

Dispatcher 必须保护来源校验、方法白名单、Zod 严格参数校验、安全错误透传和内部错误脱敏。

Methods 必须保护：

- Task、Project、Session 的公开 RPC 契约
- 标题、描述、路径、ID 和状态字段边界
- 项目真实 Git 根目录规范化和重复路径拒绝
- 目录选择取消、空结果和测试隔离入口
- 任务不存在时禁止创建会话
- 未预期的 Git 校验错误不得泄漏本地路径或内部细节

测试位置：`src/main/rpc/__tests__/`

### 4.3 Renderer Data Store

必须保护：

- 首次加载的 loading 和 error 状态闭合
- Mutation 成功后的列表刷新
- Mutation 失败时的安全返回值和用户错误信息
- 任务置顶、最近访问、排序序号和更新时间的组合排序
- Task、Project、Session 缓存在创建、触达和删除后的同步
- 已加载项目会话缓存与任务会话缓存的一致更新
- 未知异常不得直接展示内部错误

测试位置：`src/renderer/src/store/data.test.ts`

### 4.4 TerminalManager

必须保护：

- PTY 创建、输入、resize、输出、退出和主动关闭生命周期
- 工作目录存在且必须是目录
- 行列尺寸、输入类型和输入长度限制
- Terminal Session 只能由创建它的 Renderer 窗口访问
- 窗口销毁时只清理该窗口拥有的 PTY
- 应用退出时清理全部 PTY
- Renderer 销毁后不得继续发送数据和退出事件

单元测试位置：`src/main/terminal/terminal-manager.test.ts`

真实运行冒烟：`scripts/electron-terminal-smoke.cjs`

### 4.5 React 组件

组件测试关注用户可见行为，不固定 Tailwind class、DOM 层级或内部 Hook 调用次数。

优先覆盖：

- 异步加载、空态、错误态和成功态切换
- 用户输入提交、状态选择和列表更新
- 删除等不可逆操作的二次确认
- 防止重复提交和异步响应覆盖新状态
- 可访问名称和键盘操作

测试与组件放在同一目录，使用 `*.test.tsx` 命名。

### 4.6 Electron 黄金链路

当前黄金链路包括：

1. 创建任务、修改状态、创建工作会话，重启后数据仍可恢复。
2. 删除任务必须确认，并级联删除其工作会话。
3. 项目被任务引用时不可删除，解除引用后可以删除。

E2E 必须使用临时 `userData`，串行执行并在结束时关闭 Electron、删除临时目录。失败时保留截图和 trace。

测试位置：`tests/e2e/devstation.e2e.spec.ts`

## 5. 架构和安全门禁

架构规则由 `.dependency-cruiser.cjs` 执行，当前要求：

- 禁止循环依赖和不可解析依赖。
- Renderer 不得依赖 Node、Electron、Main 或 Preload 实现。
- Preload 不得依赖 Main 或 Renderer。
- Shared 必须保持平台无关，不得依赖 Electron、Node、React 或应用层实现。
- Main 不得依赖 Renderer 或 Preload。
- 生产代码不得引用测试模块。

Electron 安全配置还应由测试或静态检查持续保护：

- `contextIsolation: true`
- `nodeIntegration: false`
- `sandbox: true`
- RPC 调用校验发送者窗口
- 非应用导航被拒绝，外部 HTTP(S) 链接交给系统浏览器
- Preload 仅暴露明确白名单 API

## 6. 覆盖率策略

覆盖率是发现未受保护代码和防止测试倒退的门禁，不是测试价值的替代指标。配置文件 `vitest.config.ts` 是阈值的唯一事实来源。

当前最低门禁：

| 范围                | 语句 | 分支 | 函数 |   行 |
| ------------------- | ---: | ---: | ---: | ---: |
| 全局                |  47% |  34% |  39% |  50% |
| Database            |  85% |  65% |  85% |  90% |
| Git                 |  80% |  65% |  80% |  90% |
| RPC 整体            |  97% |  88% |  95% |  97% |
| RPC Methods         | 100% |  95% | 100% | 100% |
| Renderer Data Store |  99% |  90% | 100% |  99% |
| TerminalManager     | 100% |  95% | 100% | 100% |

阈值调整规则：

- 新功能应附带与风险匹配的测试，不能依靠现有余量吸收未覆盖代码。
- 覆盖率提升后应同步提高阈值，使新基线不可倒退。
- 不得为了通过 CI 删除有效测试、排除生产文件或降低阈值。
- 确需降低阈值时，PR 必须说明缺口、风险、替代验证和恢复计划。
- 100% 覆盖不代表行为完整；评审仍需检查边界和断言质量。

## 7. 质量门禁

### 7.1 本地快速门禁

```bash
npm run verify:fast
```

执行类型检查、Lint、格式检查、架构检查和单元/组件测试。适合开发过程中频繁运行。

### 7.2 PR 门禁

```bash
npm run verify:pr
```

在快速门禁基础上增加覆盖率、Electron E2E 和真实 PTY/Codex 冒烟。所有合并请求必须通过。

### 7.3 夜间门禁

```bash
npm run verify:nightly
```

在 PR 门禁基础上增加完整依赖树、许可证、高危漏洞审计和 Windows 安装包构建。

### 7.4 发布门禁

当前 `verify:release` 复用夜间门禁，只能证明 MVP 的构建和测试基线通过，不能视为正式发布批准。正式发布前还需要加入：

- 历史版本安装升级和数据迁移矩阵
- 干净安装、覆盖安装和卸载验证
- SBOM 生成与归档
- 安装包签名和签名验证
- 发布产物哈希、来源和版本一致性检查

## 8. CI 执行方式

GitHub Actions 配置位于 `.github/workflows/quality.yml`。

- Pull Request 和 `main` 分支 Push：Windows + Node.js 24，执行 `verify:pr`。
- 每日定时任务：执行 `verify:nightly`。
- PR 失败时上传覆盖率、Playwright 报告和测试结果。
- 夜间任务始终保留诊断信息和安装包，保留期为 7 天。
- CI 使用 `npm ci`，确保 `package-lock.json` 与依赖声明一致。

## 9. 测试编写规范

### 9.1 命名

测试名称应描述条件和可观察结果，例如：

```text
项目被任务引用时不可删除，解除引用后可以删除
窗口销毁时只关闭该窗口拥有的终端
加载失败后 loading 必须恢复为 false
```

避免使用“works”“test create”或“覆盖某行”等无法表达风险的名称。

### 9.2 断言

- 断言业务结果和外部契约，不断言无意义的中间变量。
- 安全测试同时断言拒绝结果和敏感信息未泄漏。
- 状态测试同时检查成功结果、缓存变化和错误清理。
- 资源测试同时检查创建、所有权、关闭和异常退出。
- 一个测试可以包含完成同一业务场景所需的多个断言，不按断言数量机械拆分。

### 9.3 Mock 边界

适合替换：Electron API、PTY 进程、系统对话框、时间、不可控网络和进程边界。

不应替换：被测业务规则、排序逻辑、错误映射、缓存更新或数据库约束。Mock 返回值必须符合真实契约，避免构造生产环境不可能出现的状态。

### 9.4 不应编写的测试

- 只验证组件能够 render，但没有用户可见结果。
- 只验证 Mock 调用次数，无法说明业务语义。
- 固定 CSS class、DOM 层级或内部函数调用顺序。
- 与已有测试保护同一风险、没有新增边界的重复测试。
- 依赖等待固定时间、执行顺序或开发者本地环境的测试。

## 10. 失败处理和演进

测试失败时按以下顺序处理：

1. 判断是产品回归、测试契约错误还是环境问题。
2. 产品回归必须修复实现，不得放宽断言。
3. 测试契约错误应改为验证稳定的外部行为。
4. 环境问题应消除外部依赖或增加明确的环境前置检查。
5. 不稳定测试不得长期依赖重试；应修复隔离、等待条件或生命周期。

新增模块时，在设计阶段明确：

- 关键契约和失败模式
- 最合适的测试层级
- 是否涉及 Electron 安全边界
- 是否需要临时数据、历史 fixture 或真实进程
- 应加入哪个质量门禁

## 11. 下一步建设重点

按照当前风险，后续优先补充：

1. Preload API 白名单与 Renderer/Main 跨进程契约测试。
2. TerminalPane 与 TerminalManager 的事件订阅、取消订阅和异常退出集成测试。
3. Main 进程窗口安全配置、导航拦截和数据库启动失败测试。
4. SQLite 多历史版本 fixture 和真实升级矩阵。
5. Windows 安装、升级、卸载和签名验证自动化。

新增测试应以风险下降为验收结果，不以测试数量为验收结果。
