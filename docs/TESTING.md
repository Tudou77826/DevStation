# DevStation 测试体系

测试体系用于阻止用户链路、数据一致性、Electron 安全边界和交付物质量发生回归。测试数量和覆盖率不是目标；每个测试必须能说明其保护的风险。

## 有价值的测试

测试至少保护一项：

- 关键业务规则或用户链路；
- 安全、权限或跨进程边界；
- 数据约束、迁移或缓存一致性；
- 异步、进程或资源清理行为；
- 曾发生且可能复发的缺陷；
- 第三方、文件系统或原生模块契约。

优先断言可观察结果，不固定私有调用顺序、DOM 层级或 CSS class。能由单元测试稳定覆盖的逻辑不放到 E2E；跨进程、真实渲染、持久化重启和真实 PTY 才使用较重测试。

## 防护分层

| 层级         | 保护内容                   | 工具                         |
| ------------ | -------------------------- | ---------------------------- |
| 静态质量     | 类型、Lint、格式           | TypeScript、Oxlint、Prettier |
| 架构         | 循环、反向和跨层依赖       | dependency-cruiser           |
| 单元与组件   | 领域规则、状态、React 交互 | Vitest、Testing Library      |
| 集成         | SQLite、RPC、Git、文件系统 | Vitest、临时目录、真实 Git   |
| Electron E2E | 用户黄金链路和跨进程接线   | Playwright Electron          |
| 原生冒烟     | PTY I/O、resize、进程退出  | Electron、node-pty           |
| 供应链与交付 | 依赖、许可证、漏洞、安装包 | npm、electron-builder        |

## 重点契约

| 模块            | 必须保护的行为                                   |
| --------------- | ------------------------------------------------ |
| SQLite          | 原子迁移、降级拒绝、外键、唯一性、级联和限制删除 |
| RPC             | 发送者校验、方法白名单、严格参数、错误脱敏       |
| Data Store      | loading 闭合、失败回退、排序和多缓存一致性       |
| TerminalManager | PTY 生命周期、窗口归属、输入边界和退出清理       |
| React UI        | 加载、空态、错误态、用户操作和危险操作确认       |
| Electron E2E    | 隔离 `userData`、重启恢复、引用约束和关键链路    |

当前测试位置见[代码地图](./CODE_MAP.md)。覆盖率阈值以 [`vitest.config.ts`](../vitest.config.ts) 为唯一事实来源；不得通过排除生产代码或降低阈值处理回归。

## 质量门禁

```bash
npm run verify:fast      # 类型、Lint、格式、架构、单元和组件测试
npm run verify:pr        # fast + 覆盖率 + Electron E2E + PTY 冒烟
npm run verify:nightly   # PR + 依赖、许可证、漏洞和 Windows 安装包
```

Pull Request 和 `main` Push 执行 PR 门禁；每日任务执行夜间门禁。E2E 失败保留截图和 trace。

当前 `verify:release` 复用夜间门禁，不代表正式发布批准。发布前还需要历史版本升级、干净安装、卸载、SBOM、签名和产物一致性验证。

## 编写规则

- 测试名称描述“条件 + 可观察结果”，不使用 `works` 或“覆盖某行”。
- 正常路径和关键失败路径同等重要。
- SQLite 和 Electron 测试使用独立临时数据，不依赖开发者环境。
- 只在进程、时间、文件系统、Electron API 等不可控边界使用 Mock，不 Mock 被测业务规则。
- 安全测试同时断言拒绝结果和敏感信息未泄漏。
- 资源测试同时检查创建、所有权、关闭和异常退出。
- Playwright 不启用重试；不稳定测试应修复隔离、等待条件或生命周期。

以下测试通常没有价值：只验证组件能 render、只验证 Mock 次数却没有业务语义、固定实现细节、重复保护同一风险，或依赖固定等待时间和本地已有数据。

## 随版本演进

1. 设计功能时先识别关键契约、失败模式和测试层级。
2. 实现时让测试与代码一起提交。
3. 修复缺陷时先在最接近根因的层级复现，再修复实现。
4. 覆盖率提高后同步提高阈值，防止基线倒退。
5. 新增进程边界、数据迁移或发布能力时，将验证加入对应门禁。

下一步优先补充 Preload API 白名单、TerminalPane 跨进程链路、Main 窗口安全配置和历史数据库升级矩阵。
